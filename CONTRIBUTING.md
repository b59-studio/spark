# Contributing to TX*SPARK

Thank you for helping build grassroots civic-tech for Texans. This guide
covers how we branch, commit, test, and open pull requests.

## Before you start

1. Read [`docs/onboarding.md`](docs/onboarding.md) for local setup.

If `docs/` never appears in `git status`, the coding-standards installer may
have added `/docs` to `.git/info/exclude`. Remove that line locally so
project docs (`architecture.md`, `onboarding.md`, `adr/`) can be committed.
Bundle-only paths under `docs/` stay ignored via `.gitignore`.
2. Skim [`docs/architecture.md`](docs/architecture.md) for system context.
3. Check [`standards/99-project-overrides.md`](standards/99-project-overrides.md)
   for repo-specific layout and import rules.

## Branch strategy

- Base branch: **`main`** (protected; merge via PR).
- Branch names: `feat/short-description`, `fix/short-description`,
  `docs/short-description`, `chore/short-description`.
- Keep PRs focused — one logical change per PR when possible.
- Large map or schema work: coordinate in an issue first; note if changes
  touch `map-migration/` vs `src/`.

## Commit messages

- **Subject:** imperative mood, ≤72 characters  
  Good: `fix: reject unsigned WooCommerce webhooks in production`  
  Avoid: `Fixed stuff`, `WIP`
- **Body (optional):** explain *why*, link issues (`Fixes #123`), note
  follow-ups or deployment steps.
- **Conventional Commits** are encouraged:

  | Prefix | Use for |
  | ------ | ------- |
  | `feat:` | New user-visible behavior |
  | `fix:` | Bug fixes |
  | `docs:` | Documentation only |
  | `refactor:` | Code change without behavior change |
  | `test:` | Tests only |
  | `chore:` | Tooling, deps, CI |
  | `perf:` | Performance |
  | `ci:` | CI/CD |

- Do not include AI tool names, "generated by", or `Co-authored-by` lines
  for assistants in commits or PRs.

## Pull requests

1. Update docs in the **same PR** when behavior or env vars change
   (README, `docs/`, `env/*.example`, `db/README.md`).
2. Add or update tests for non-trivial logic (`npm test` must pass).
3. Run `npm run lint` before requesting review.
4. For new dependencies, note license and maintenance in the PR description.
5. Fill out the PR template (if present) with **Summary** and **Test plan**
   checklist items you actually ran.

### Review expectations

- At least one maintainer approval before merge.
- Address review comments with new commits (squash on merge is fine).
- Security-sensitive changes (auth, webhooks, PII) need explicit test plan
  steps in the PR.

## Testing

```bash
npm test          # Vitest — required for PRs touching src/
npm run lint      # ESLint
npm run build     # Recommended before large UI or routing changes
```

Integration tests may require env vars; tests should skip or mock when URLs
are unset. Do not commit real secrets to reproduce failures.

## Database changes

- **Analytics:** add numbered SQL under `db/migrations/analytics/`, document
  in [`db/README.md`](db/README.md), run `npm run analytics:migrate` locally.
- **Map / core (Prisma):** follow procedures in `map-migration/` until merged;
  do not apply map migrations to production without team sign-off.

## Architectural decisions

Significant choices (new datastore, auth model, split services) need an ADR in
`docs/adr/` before or with the implementing PR. Use the next number:
`docs/adr/NNNN-short-title.md`. Status: Proposed → Accepted → Superseded.

## CHANGELOG

User-visible changes should appear under `[Unreleased]` in
[`CHANGELOG.md`](CHANGELOG.md) (Added / Changed / Deprecated / Removed /
Fixed / Security). Release maintainers cut version sections when tagging.

## Privacy and security

- Never commit `.env`, `.env.local`, API keys, or exports with PII.
- Use `env/*.example` for new variables with placeholder values.
- Report vulnerabilities privately to project maintainers (do not open public
  issues for active exploits).
